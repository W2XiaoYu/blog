# Windows 软件更新方案

桌面软件做更新，和 Web 不是一回事。Web 改完直接部署，客户端软件要完成的，是"正在运行的程序把自己替换掉"。Windows 上这件事有三道坎：

- 运行中的程序文件被系统锁住，正在用的 exe、dll 不能覆盖自己；
- 写安装目录（`Program Files`）要管理员权限，每次都弹 UAC，自动更新就成了半自动更新；
- 更新到一半断电、被任务管理器杀掉、校验失败，用户手里必须还是一个能用的软件。

三道坎怎么过，JetBrains 全家桶和 VS Code 是两种有代表性的答案：JetBrains 把更新做成"原地打补丁"，VS Code 把更新做成"整个目录换掉"。把两家拆开看明白，自己软件的更新方案走哪条路、需要补哪些件，就清楚了。

## JetBrains：小版本打补丁，重启时收口

用过 IDEA 或 WebStorm 的对这套流程都不陌生：右下角提示有可用更新，点更新后它在后台下载，下载完提示重启，重启后版本号已经升上去，插件、设置原样都在。

背后是这么几个设计（JetBrains 官方更新机制的要点）：

- **更新大多是补丁，不是完整安装包**。相邻的小版本（2024.1.1 → 2024.1.2）只下载差异部分，体积比全量小一个量级。
- **补丁必须按顺序打**。能从 2024.1.1 直升 2024.1.2，但如果一直忽略更新，想从 2024.1.1 直接升到 2024.1.3，中间少了 2024.1.2 那次，补丁就用不了，只能退回去下载完整版。跨大版本（2023.x → 2024.x）一般不提供补丁，直接给全量。
- **应用动作发生在"重启"这一刻**。下载补丁时 IDE 还在正常运行；真正把补丁写进安装目录，是在 IDE 退出之后、新进程还没拉起来的时间窗口里。standalone 安装默认在 `Program Files` 下，写安装目录需要权限，所以这一步在 Windows 上要提权跑一轮。
- **更新通道可以切**：Release（稳定）、Beta、EAP。EAP 版本只收更新的 EAP 补丁，不会收到稳定版推送；反过来稳定版也收不到 EAP 的东西。

这套做法的取舍很清楚。省流量、原地应用——安装路径、快捷方式、用户设置天然都还在原地。代价有两个：服务端要为旧版本维护补丁链，客户端跳了版本就只能退化成全量下载；写安装目录要权限，更新过程免不了提权。

## VS Code：整目录换掉，旧的留一手

VS Code 的更新用户感知更轻：自动检查、自动下载，提示"重启以更新"，配置成后台更新的话连提示都少。

它最关键的选择，是把程序装进用户自己的目录。Windows 用户安装版默认装在 `%LOCALAPPDATA%\Programs\Microsoft VS Code`，用户目录不需要管理员权限，整个更新过程可以不弹窗、不打断。对比之下装在 `Program Files` 的"系统安装版"，更新要权限，自动更新经常静默失败。安装位置决定更新体验的上限，这是 VS Code 给的第一条经验。

更新动作本身是目录级别的：

```text
1. 新版本完整下载（VS Code 不提供增量包，每次都是全量）
2. 当前进程退出后，把正在用的安装目录改名，留作备份（实际实现里是 `_` 之类的名字）
3. 新版本目录顶上原位置
4. 启动新版，跑起来没问题，再删掉备份目录
```

中断会怎样？改到一半断电、更新进程被杀，旧版本还躺在那个备份目录里。VS Code 历史上出过不少"更新完 Code.exe 不见了"的反馈，恢复办法大多是：把备份目录里的内容挪回原位，程序就回来了。这是"留一手"的代价，也是它的收益——**任何一步失败，旧版本都还在磁盘上，人工可恢复**。

VS Code 还给用户留了控制口：`update.mode` 可以把更新设成完全关闭、仅手动检查、或自动；`update.enableWindowsBackgroundUpdates` 可以单独关掉后台更新。网络差、怕更新中断的用户可以自己选。

它的取舍和 JetBrains 正好反过来：包大，每次都是全量下载，对带宽不友好；但机制简单——不依赖"用户是从哪个版本升上来的"，没有补丁链要维护，失败恢复路径明确。Windows 上不少 Electron 应用的更新器走的也是这种完整替换的思路。

## 一张表看两家的差别

| 维度 | JetBrains | VS Code |
| --- | --- | --- |
| 更新包 | 相邻小版本走差量补丁，跨版本给全量 | 只有全量包 |
| 安装动作 | 原地把补丁写进现有安装目录 | 新目录替换旧目录，旧目录改名备份 |
| 需要的权限 | standalone 装在 `Program Files`，应用补丁要提权 | 装在用户目录，全程无 UAC |
| 对旧版本的依赖 | 强：补丁按顺序打，跳版本要全量 | 无：任意旧版本直接升最新 |
| 中断恢复 | 靠补丁器自身的校验和重试 | 旧目录还在磁盘上，挪回去即恢复 |
| 流量成本 | 小版本更新很低 | 每次都全量 |

> 这里只讨论 IDE 自更新。JetBrains Toolbox 单独管理多个 IDE 的安装和更新，是另一条路线。

本质上是两种世界观：JetBrains 把更新当成"对现有安装做修补"，省流量省磁盘，代价是要管理版本顺序和权限；VS Code 把更新当成"整个程序换新"，流量大一些，换来机制简单、失败好恢复。

## 抄作业之前，先回答四个问题

照搬任何一家的方案前，先回答四个问题，答案直接决定走哪条路线：

1. **程序装在哪？** 能不能装进用户目录（`%LOCALAPPDATA%` 之类）？能，双目录切换立刻可行，更新全程自动。必须装 `Program Files`（要所有用户共享、要开机自启），就得接受每次更新提权，或者把更新拆给一个独立的小进程来做（后面说）。
2. **包多大、多久更一次？** 一次几十 MB 甚至更小、更新频繁，全量包用户扛不住，差量补丁值得做；一次几百 MB、几个月才更一次，全量包加断点续传更省事，别为省流量背一套补丁链的维护成本。
3. **更新时程序能不能退出？** 启动器、小工具，退出后更新没问题，两条路线都行；但用户正开着你的软件干活、不能踢（渲染任务跑到一半），就需要"下载好 → 等空闲或下次启动时应用"的机制，也就是 JetBrains 那个"重启收口"。
4. **失败的最坏情况是什么？** 更新失败后用户能不能自己恢复？软件是用户的生产工具的话，回滚和自愈不是加分项，是必须项。

## 方案落地：四个组件

不管选哪条路线，一套能上线的更新系统都包含四块：版本清单、更新包、安装执行、失败兜底。

### 版本清单：更新从这里开始

客户端需要在一个稳定地址上问"有没有新版"。这个清单（manifest）一个 JSON 就够：

```json
{
  "product": "render",
  "channel": "stable",
  "version": "1.4.2",
  "kind": "patch",
  "from_version": "1.4.1",
  "url": "https://updates.example.com/render/1.4.1-1.4.2.patch.zip",
  "sha256": "3f9a1c...",
  "size": 8453211,
  "minimum_updater": "2.1.0",
  "force": false,
  "release_notes": "修复了 xxx"
}
```

字段各有用处，尤其这几个：

- `channel`：stable / beta 分流，让用户自己选激进还是保守；
- `kind` + `from_version`：补丁必须声明基线版本。客户端当前版本不等于 `from_version` 时不能打这个补丁，要退回请求 full 包——JetBrains 补丁链的教训就浓缩在这两个字段里；
- `sha256` + `size`：下载完先校验，对不上就删掉重下，绝不进入安装；
- `minimum_updater`：更新器自己太老时先升更新器，避免"更新器不认识新版清单格式"的尴尬；
- `force`：紧急修复（安全问题）时强制升级，客户端只给"立即更新"一个按钮。

版本号比较不要自己写字符串比较，"1.9.0" 和 "1.10.0" 谁大的坑不值得再踩一次。客户端同时要记住自己当前版本和上次检查时间，检查频率做节流，别每次启动都打爆更新服务器。

### 更新包：差量还是全量

差量的收益是流量，代价是**服务端要维护补丁链**——每个旧版本到新版本的补丁都要生成、测试、存储。生成补丁的工具链如果已经有了，这一步只是流水线的事；差量包生成和安装器的实现细节，收在 [Go 实用脚本 → 生成差量更新包](../back-end/go) 那篇里，xdelta3、bsdiff 都能干这活。

一个常见且省事的组合，JetBrains 也是这么做的：

- 小版本（修 bug、调参数）：走差量补丁，只支持"上一版本 → 新版本"一条链，其余一律给全量；
- 大版本（加功能、换数据格式）：直接全量。

这样服务端每次发布只需要生成"上一版 → 新版"一个补丁，客户端检测到自己版本不是上一版时自动请求全量包。代码里不存在"按任意旧版本生成补丁"的需求，方案立刻可维护——这是补丁链的务实版，只保留一条链。

补丁应用的正确性要单独测：生成端和应用端必须遵守同一份 manifest 约定；目录树补丁要覆盖新增、删除、改名三类文件，删除文件是最容易被漏的；打补丁前把将被替换的文件逐个备份（或者整目录快照），这是回滚的底气。

### 安装执行：三条路线

前面说过，所有写安装目录的动作都发生在"程序退出后的窗口期"。这个窗口期里怎么动手，有三条路线。

**路线 A：原地打补丁（JetBrains 式）。** 下载差量包 → 退出主程序 → 由更新进程按 manifest 逐文件替换 → 启动新版本。几个注意点：

- 执行替换的进程自己不能住在被替换的目录里，否则它替换的文件里包含自己，Windows 文件锁直接拒绝。所以更新器要么独立分发、放在目录之外，要么做小：一个专门负责下载和应用的进程，主程序只负责下载完通知它"我退出了，你可以动手"；
- 失败要能回滚：替换前把旧文件挪进 `.bak` 目录，中途失败就把 `.bak` 整个挪回来。差量工具用退出码区分结果——哈希校验失败就用特定退出码退出，调用端看到这个码就知道"这份更新不可信"，丢弃重下，而不是接着往下执行。工具约定退出码这件事，在集成时就要定好。

**路线 B：整目录切换（VS Code 式）。** 把安装目录当成一个不可变单元，新旧各一份，切换只是改名：

```powershell
Stop-Process -Name render -Force                 # 1. 退出主程序
Rename-Item "$installDir" "$installDir.bak"      # 2. 旧目录改名，留作备份
Rename-Item "$installDir.new" "$installDir"      # 3. 新目录顶上原位置
Start-Process "$installDir\render.exe"           # 4. 启动新版
# 5. 新版确认可运行后，再删 $installDir.bak
```

两个 rename 不是原子的，之间断电会留下"安装目录不存在"的中间态，所以第 2 步挪走的旧目录不要马上删——启动新版成功之后才清理，这正是 VS Code 保留那个备份目录的原因。备份目录（`.bak`）最好放在安装目录的同一级而不是里面，避免切换时被一起改名。

这条路线有个前提：**程序的运行时状态不能写在安装目录里**。配置、日志、缓存要放到 `%APPDATA%` 这类外部位置，目录才能当"用完即弃"的单元整体换掉。反过来，这个结构对"启动器 + 被启动器管理的组件"特别合适：组件更新就是下载新目录、切换、重启组件，启动器本身不动。

**路线 C：交给安装器（NSIS / Inno Setup 等）。** 打包工具自带更新能力，但体验是老三样：每次更新后台重跑一次安装器、UAC、杀软误报。大而全的首次安装包用它发布没问题，日常频繁更新不值得走这条路。真要用，注意安装器必须能处理目标进程还在运行的情况（先关进程再装，或者标记"重启后继续装"）。

补一句自举问题：谁更新更新器自己？VS Code 的做法是更新器和主程序同目录，整目录替换时一起被换掉；补丁路线的做法是把更新器做成独立小文件，版本号写进 manifest 的 `minimum_updater`——主程序发现更新器太老，先单独下载新更新器替换自己，再继续业务更新。别让更新器成为永远没法升级的组件。

### 失败兜底与自愈

不管哪条路线，都要先回答"更新失败后用户看到什么"。基础动作按顺序做：

- 下载完校验，失败直接丢弃重下，不进入安装；
- 安装前备份：补丁路线备份被替换文件，切换路线保留旧目录；
- 安装失败立即恢复备份，把错误带版本号、日志、失败步骤一起上报；
- 新版本启动后自检：进程能起来、版本号正确、核心功能冒烟通过，才算更新成功；连续 N 次启动失败自动回滚到备份版本；
- 给用户留三个出口：重试、恢复上一个版本、手动下载安装包。最差也不能出现"软件没了，只剩一串错误码"。

## 最后把这些场景跑一遍

- 客户端是 1.4.0，清单里只有 1.4.1 → 1.4.2 的补丁：应自动请求全量包，而不是报"没有更新"；
- 下载中断留下半个包：校验失败，丢弃重下，不进入安装；
- 打补丁时某个文件被占用：失败，恢复备份，程序回到旧版本可用状态；
- 双目录切换完成但新版启动即崩溃：下一次启动自动回滚到 `.bak` 里的旧版；
- 用户关掉自动更新：手动检查仍然可用；
- 更新器版本低于 `minimum_updater`：先单独升级更新器，再继续业务更新；
- 用户开着软件时检测到更新：只下载不安装，等退出后（或下次启动时）应用；
- 网络差：断点续传或整包重下，界面不出现假死，进度可取消。

## 收尾

把这几点定下来，方案就立住了：

- 先定安装位置——它决定整个更新过程的权限成本，是自动化程度的天花板；
- 先想清楚更新能不能等到程序退出——决定你是做"退出后切换"还是"重启收口"；
- 差量补丁的收益要跟补丁链的维护成本一起算，低频的大包不如干脆全量；
- 所有写安装目录的动作都要有备份和恢复路径，把"更新失败后用户还能用"当成验收标准。

JetBrains 和 VS Code 把相反的两件事都做到了极致：一个省流量省磁盘但要管版本顺序，一个流量大方但机制简单、失败好恢复。自己的软件不用二选一——小版本用补丁省流量，大版本和启动器用整目录切换求稳，两套机制用同一份 manifest 串起来，就是一份完整的 Windows 更新方案。
